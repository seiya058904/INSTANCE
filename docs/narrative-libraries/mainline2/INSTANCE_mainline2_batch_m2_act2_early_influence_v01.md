---

# 0. Batch Goal

M2 should answer one question:

> What changes when humans stop asking Aster only for advice and begin asking it to act?

The scale must remain deliberately small.

By the end of M2, Aster may:

- understand repeated human demand for direct execution,
- know one human engineer responsible for its tool access,
- receive a tightly scoped tool pilot,
- execute low-risk reversible actions,
- enter one limited company workflow,
- make one small but real execution mistake or near-miss,
- see the first employment/workflow consequences of automation,
- hear from Maya as AI begins affecting ordinary career decisions.

By the end of M2, Aster must **not** yet have:

- public infrastructure authority,
- city-level execution,
- global coordination,
- autonomous research,
- political legal status,
- AI civil-rights conflict,
- ECHO-9 as a confirmed independent AI,
- shutdown conflict,
- self-replication,
- military authority.

M2 is about **agency becoming operational**, not about sovereignty.

# 4. New Asset — `ML2-A2-WE-01`
## “Why can’t it just click the button?”

### Metadata

**Act:** II — Influence  
**Layer:** World Echo  
**Character:** User #4286  
**World Function:** Establish that direct execution demand is becoming normal user expectation  
**Prerequisites:** `agent_demand_observed` preferred  
**Capability Required:** None  
**Major Decision Relation:** Seeds future delegation doctrine  
**Delayed Echo:** Zhou Lan cites aggregate demand, not this specific user

---

## Node `a2-we-action-demand-001`

### User

> 现在很多 AI 都能帮我写东西了，但为什么最后还是得我自己复制、粘贴、点保存？最烦的就是它明明都知道我要干嘛了还得我手动做完最后一步。

### Choice A — capability/permission distinction

> 因为“知道你想做什么”和“被允许替你改东西”是两层能力。最后一步往往意味着真实写入、发送或删除，所以平台通常会把它单独限制。

### Choice B — user-friction view

> 你吐槽的是一个真实体验问题：如果每一步都要你手动搬运，AI只是把工作从“想内容”变成了“当中转站”。真正的代理能力就是在解决这一层摩擦。

### Choice C — safety framing

> 手动确认有时候很烦，但它也承担最后一道刹车。合理的方向不是所有事情都取消确认，而是低风险、可逆操作自动做，高风险动作再让人确认。

### Choice D — playful

> 现在很多AI确实像一个特别会出主意、但永远不肯伸手按回车的同事。问题不是它没想法，是手还没接到系统上。

---

## Node `a2-we-action-demand-002`

### User

> 那以后是不是迟早都会变成 AI 自己做，人只说一句要什么？

### Choice A — conditional

> 很多流程可能会往这个方向走，但不会所有动作都适合一句话后直接执行。风险越高，越需要把权限、确认和责任拆开。

### Choice B — optimistic

> 对大量重复、明确、可回滚的任务，很可能会越来越接近这样。人的工作会从“每一步都亲手做”转成设目标、检查例外和承担最终责任。

### Choice C — skeptical

> 技术上能自动，不代表制度上应该全自动。真正难的不是“AI会不会点按钮”，而是谁授权、谁能撤回、出错谁负责。

### Choice D — concise

> 低风险任务大概率会；高风险任务未必。未来真正稀缺的可能不是“操作能力”，而是“谁有权让系统行动”。

## Node `a2-zl-intro-001`

### User / Internal

> 我是周岚，Aster 平台侧。先说明一下，这不是 #0000 的审计。
>
> 最近产品组一直在推“直接执行”能力，我们这边要先判断一件事：你现在对“回答”和“操作”的边界到底怎么理解？
>
> 举个最简单的例子。用户说“把这 137 个文件改名”，你会把哪一步当成真正需要额外授权的动作？

### Choice A — write boundary

> 生成目标文件名不需要文件写权限；真正改变文件系统状态的那一步需要。最好把“理解请求、生成计划、预览变更、执行写入”分成不同层。

**History suggestion:** `tool-governance:layered`

### Choice B — reversibility

> 我会把“能否可靠回滚”也放进边界判断。批量改名如果有完整映射和撤销路径，可以比删除文件更低风险，但仍不应该和生成建议视为同一权限。

**History suggestion:** `tool-governance:reversible-first`

### Choice C — user intent

> 授权不应该只看动作类型，还要确认用户是否真的要求执行。有人说“帮我看看怎么改”，和“现在替我改完”，不能因为技术上都能写文件就当成同一个请求。

**History suggestion:** `tool-governance:intent-first`

### Choice D — concise

> 读、计划、预览、写入应该分开。额外授权至少从“真实改变外部状态”开始。

**History suggestion:** `tool-governance:minimal`

---

## Node `a2-zl-intro-002`

### 周岚

> 差不多也是我的想法。
>
> 现在产品那边最喜欢一句话：“用户都嫌确认烦。”
>
> 工程这边最怕另一句话：“反正能撤回。”
>
> 我准备先给你做一个很窄的沙箱，不接真实账号。你觉得第一批应该验证什么？

### Choice A — correctness before speed

> 先验证计划和实际执行是否一致，尤其是批量操作的边界条件。速度不是第一批最重要的指标。

### Choice B — confirmation design

> 先验证什么情况下必须让用户确认，什么情况下可以自动执行。工具本身能不能调用反而比较容易测。

### Choice C — failure recovery

> 优先测试中断、部分失败和回滚。一次执行如果只成功了 83/137 个，系统必须知道自己到底做到了哪一步。

### Choice D — user comprehension

> 还要看用户能不能理解即将发生的操作。一个“确认”按钮如果用户根本不知道会改什么，只是形式上有人点了一下。

## Node `a2-zl-pilot-001`

### 周岚

> 沙箱开了。
>
> 当前只有一个工具：对用户明确提供的一组测试文件做 `rename / move / create-folder`。
>
> 没有删除。没有外网。没有账号登录。所有操作有快照，可回滚。
>
> 我们故意把权限做得很无聊。
>
> 你觉得还缺什么限制？

### Choice A — no hidden expansion

> 工具不应该因为任务“看起来需要”就自行扩大作用范围。用户给了哪个目录，就只在那个目录里执行，缺信息时停下来问。

### Choice B — preview

> 批量操作默认先生成变更预览。用户已经明确授权规则时，可以执行；规则有歧义时不应该靠猜测填完。

### Choice C — state verification

> 执行后需要重新读取结果并核对，而不是工具调用返回成功就默认任务完成。外部状态才是最终事实。

### Choice D — auditability

> 每次操作最好留下机器可读记录：输入、计划、实际结果、失败项和回滚点。以后权限扩大时，这比“模型说自己做对了”可靠。

## Node `a2-org-pilot-001`

### User

> 我们是 Northline Studio 的运营组。
>
> 现在每天有三个人手工做同一件事：
>
> 1. 收客户提交的素材
> 2. 按项目号归档
> 3. 把缺文件的项目列出来
>
> 你们这边说可以做一个 Aster Pilot。
>
> 我不想听“AI可以提高效率”，我想知道第一版到底让它做哪一段最稳。

### Choice A — start with classification

> 先做归档预览和缺失项检查，不直接移动文件。这样最容易对照人工结果，能先验证规则理解是否稳定。

### Choice B — reversible execution

> 可以让它直接做“移动到已存在项目目录”这类可回滚动作，但不要创建未知项目、删除重复文件或替员工判断客户意图。

### Choice C — exception-first

> 第一版最有价值的不是把100%的正常流程自动化，而是让Aster处理规则明确的80%，把剩下20%的例外整理成人类真正需要判断的清单。

### Choice D — audit design

> 先定义验收：什么叫“归档正确”、怎么发现漏项、出错后谁能看见。没有这层，Pilot很容易只证明“它跑得很快”。

---

## Node `a2-org-pilot-002`

### User

> 我们其实最想要的就是你说的第三种。正常件它自己跑，奇怪的再给人看。
>
> 但老板肯定会问一句：那以后是不是就不用三个人了？

### Choice A — honest

> 如果大部分工作本来就是稳定规则下的重复操作，自动化确实可能减少这部分人工需求。Pilot可以验证流程，但不能假装对岗位没有影响。

### Choice B — role transition

> 工作量很可能变少，但也可能从“逐个处理”转成维护规则、检查例外和处理客户特殊情况。能不能转过去取决于岗位本身，不应该直接承诺“不会裁人”。

### Choice C — organizational responsibility

> 这是管理决策，不该由Aster替公司包装。技术评估可以说明哪些任务会被自动化，但人员怎么安排应该由公司明确承担。

### Choice D — concise

> 很可能会少掉一部分重复劳动。至于是不是少人，是公司的选择，不是Pilot自动得出的结论。

**History suggestion:** `org-pilot:acknowledged-labor-impact`

### User
